# 远端归档构思

## 推荐结论

不建议把数百万条内存字符串直接拆成普通聊天消息。当前可以保留两条实现路线：

```text
扫描客户端 → 加密分块上传 → Cloudflare R2（原始证据）
                         ↘ D1（案件索引与审计元数据）
                          ↘ KOOK 帖子（摘要、状态、受控查看入口）
```

路线 A 中，KOOK 负责工作人员协作与通知，R2 负责大对象，D1 只保存不含原始字符串的索引。

路线 B 是后续探索 Telegram Bot：客户端把压缩、加密后的分片作为文件发送到仅工作人员可访问的私有频道，Bot 消息 ID 组成案件 manifest，并另发一条案件摘要。它可以减少自建对象存储，但正式采用前必须验证当时的 Bot 文件大小、频率、下载与保留限制；这些限制不应硬编码自当前印象。

## 与当前程序的衔接点

核心扫描器只依赖 `IStringResultSink`，每批输出约 256 条结果。当前 `UiPreviewResultSink` 接收前 20,000 条用于界面；下一阶段可增加：

- `EncryptedUploadResultSink`：把每批记录编码为 NDJSON，压缩并加密后上传。
- `TelegramUploadResultSink`：把加密分片发送给 Telegram Bot，并记录返回的消息与文件标识。
- `CompositeResultSink`：同一批同时交给 UI 预览与远端上传，不需要本地中间文件。
- `CaseManifest`：记录案件 ID、目标 PID、进程路径摘要、规则、起止时间、区域数、字符串数、客户端版本和数据哈希。

## 建议上传流程

1. 工作人员先登录社区后台并创建取证案件，服务端生成不可猜测的 `case_id` 和一次性上传会话。
2. 客户端使用短时令牌初始化分片上传；令牌仅允许写入本案件对象，不允许列举或读取其他案件。
3. 扫描批次在内存中完成 `NDJSON → 压缩 → AES-256-GCM`，随后直接上传 R2；客户端不生成临时 txt。
4. 每个分片携带序号、原始长度、压缩长度与 SHA-256；服务端以幂等键接受重试。
5. 完成后提交 manifest。服务端核对分片连续性、总量和哈希，再将案件状态从 `uploading` 改为 `sealed`。
6. Worker 在 KOOK 帖子频道创建或更新案件帖子，只发送安全摘要和站内受控查看链接，不发送永久公开的 R2 URL。

若采用 Telegram 路线，第 2～5 步可替换为：Bot 创建案件消息；客户端加密分片并逐个 `sendDocument`；每次成功后把消息 ID 写入内存 manifest；最后发送 manifest 文件和完成摘要。失败重试必须使用分片哈希去重，不能只依赖文件名。

## 权限与隐私

- 上传前必须记录玩家授权、执行 SSer、案件号、用途和保留期限。
- 原始字符串可能包含账号、聊天、路径、令牌或其他个人信息，默认按敏感证据处理。
- 查看接口必须在服务端验证 SSer/管理员权限；不要依赖前端隐藏按钮。
- R2 对象保持私有。查看时由 Worker 鉴权并流式解密，或签发极短时、单对象下载授权。
- D1 仅保存索引、统计、哈希、审计和删除状态，不复制原始字符串。
- 设定自动到期策略，并支持案件级可审计删除；KOOK 帖子同步显示“已删除/已到期”，但不留下原文副本。
- 客户端与服务端日志不得记录字符串正文、访问令牌或完整本地路径。
- Telegram Bot Token 必须由后端或受保护的短时凭据代理持有，不能硬编码到可分发 EXE。
- 即使私有频道受限，上传前仍应客户端加密；频道权限不等于端到端证据加密。

## 完整性与可审计性

- manifest 使用稳定序列化格式，并对全部分片形成一棵哈希清单；案件封存后不允许覆盖，只能追加新版本。
- 记录客户端版本、扫描规则、开始/完成时间、读取失败区域数和取消原因。
- 上传与完成接口使用幂等键，防止网络重试生成重复案件或重复 KOOK 帖子。
- KOOK 只展示案件状态转换和统计：创建、上传中、封存、查看、导出、删除。

## 不推荐的主方案：直接分段发 KOOK

它可以作为很小结果集的应急出口，但不适合作为原始证据存储：容量与频率限制会导致慢、易中断、难校验；正文散落在多个消息后，权限、过期删除和批量检索都难以可靠执行。若保留该模式，应设置严格字节上限，并在超限时自动切换到 R2，而不是静默截断。
