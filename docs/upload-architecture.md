# KOOK 加密归档架构

## 已实现的数据路径

```text
SSer/Admin 登录 screenshare.cn
        │ 生成短期上传或恢复凭证
        ▼
Undefined String Dumper
  UTF-8 证据文本 → 8 MiB 分块 → Zstandard → AES-256-GCM
        │ HTTPS；Bearer 凭证只绑定一个 archive_id
        ▼
screenshare.cn Worker
  校验用户、角色、有效期、用途与 archive_id
        │ Service Binding + 独立内部密钥
        ▼
Dashboard Worker
  校验密文 SHA-256 → KOOK Bot 上传附件 → 帖子频道 9446377666045637
        │
        └─ D1：用户归属、状态、分片哈希、KOOK 资源索引与审计事件
```

Bot Token 与归档主密钥只存在于 Dashboard Worker Secret。Dumper 不包含 Bot Token、内部服务密钥或长期解密密钥；主站也不持有归档主密钥。

## 身份与用户隔离

- 仅 `sser` 与 `admin` 可以进入主站后台的 Dumper 归档模块。
- 上传凭证有效 24 小时，首次创建会话时原子绑定一个 `archive_id`，此后不能改绑。
- 归档记录保存创建者用户 ID 与用户名快照；后台列表明确显示所属用户，并支持按用户、状态、进程和归档编号筛选。
- 恢复凭证由工作人员针对一个已封存归档签发，有效 1 小时，不能读取其他归档。
- 所有客户端 API 先在主站验证 D1 中的凭证哈希、用户状态与角色，再通过 Service Binding 调用 Dashboard Worker；客户端永远不能直接调用内部接口。
- 上传、分片发布、封存、恢复凭证签发、密钥读取与分片下载都写入审计链。日志只记录编号、字节数、状态与哈希，不记录字符串正文、凭证或数据密钥。

## 加密格式

每个归档使用随机 256 位数据密钥。Dashboard Worker 用 `DUMPER_ARCHIVE_MASTER_KEY` 通过 AES-256-GCM 包裹该数据密钥，D1 只保存包裹后的密文和随机 nonce。

每个 `.usdc` 分片独立包含：

1. 固定标记 `USDC0001`；
2. 归档 UUID 与分片序号；
3. 明文长度与压缩后长度；
4. 12 字节随机 nonce；
5. 16 字节 AES-GCM 标签；
6. Zstandard 压缩后的密文。

AAD 绑定格式版本、归档 UUID、分片序号和明文长度，因此不能把某个分片挪到另一个归档或位置。每片另算 SHA-256；最终清单还保存按顺序拼接所有分片哈希后的 SHA-256，以及完整恢复文本的 SHA-256。

当前 8 MiB 是应用内部的保守分片值，用于控制 Worker 峰值内存、重试成本与故障范围；它不是把 KOOK 普通用户上传限制套到 Bot 上。实际 Bot 能力以 KOOK API 返回和频道实测为准。

## KOOK 帖子布局

每个归档对应一个帖子：

- 主帖：归档编号、上传用户、目标进程/PID、Dumper 版本、格式和“上传中”状态，不显示命令行、路径或字符串正文。
- 分片回复：一个文件模块、序号、大小、密文 SHA-256，以及机器可回查的隐藏标记。
- 封存回复：完整性摘要和 `.usd-manifest.json` 文件。

附件通过 `/asset/create` 上传，并在帖子 CardMessage 的 `file` 模块中引用。若写请求超时，客户端先查询服务端状态；Dashboard Worker 再用归档、分片或封存标记回查 KOOK，确认未发布后才重试，避免因“响应丢失但写入成功”产生重复帖子。

## 断点续传与失败情况

- 扫描阶段：磁盘只写独立加密分片；未完成扫描无法形成合法封存清单，取消或异常会清理该不完整临时目录。
- 上传阶段：每个成功分片立即在 D1 标记为 `published`。网络中断时已完成的本地加密分片和 checkpoint 保留；重新输入有效上传凭证及同一 UUID 后跳过哈希一致的已发布分片。
- 同序号不同哈希：服务端返回冲突，不允许覆盖已发布证据。
- 分片上传成功但回帖失败：保留 `asset_uploaded` 状态，重试只补帖子引用，不重复上传附件。
- KOOK 回帖已成功但响应超时：按隐藏标记回查帖子并补齐 D1 `post_id`。
- 封存：服务端要求分片从 0 连续到 `part_count - 1`、全部为 `published`，并核对明文/密文字节总量后才生成清单和切换为 `sealed`。
- 恢复：任何下载、哈希、AES-GCM、解压、顺序或总量异常都会删除临时输出；既有目标文件不会被破坏。

## 管理人员恢复步骤

1. 在 screenshare.cn 后台打开“Dumper 归档”，按用户或编号找到记录。
2. 确认状态为“已封存”、分片数量和密文总量合理。
3. 打开详情，生成一次性显示的 1 小时恢复凭证，并优先使用“一键复制恢复信息”把凭证与绑定归档 UUID 作为一组复制。
4. 将完整恢复信息粘贴到 Dumper 的“短期凭证”框；客户端自动填入并预检归档 UUID。旧版客户端仍可分别输入两项。
5. 点击“恢复归档”。若手工输入的 UUID 与有效恢复凭证不一致，服务端仅向该凭证持有者返回其绑定 UUID，客户端自动更正后再开始下载。
6. Dumper 下载清单和数据密钥，按序流式下载各分片，逐片校验、解密、解压并写入唯一 `.partial` 文件。
7. 最终明文 SHA-256 与清单一致后，程序才把临时文件原子移动到选定路径。

## 长期保留边界

该方案把 KOOK 作为主要免费对象存储，D1 作为索引，不使用 R2 空间。Bot 帖子是否计入普通频道消息配额以实际行为为准，当前不在程序中硬编码普通用户的 5 MB/300 MB 限制。

“尽可能长期”仍不等于平台可以承诺的无限期：服务器所有者或 KOOK 平台删除内容、账号/服务器被封禁、资产策略改变，都会影响可恢复性。必须同时做到：

- 永久保留 `DUMPER_ARCHIVE_MASTER_KEY` 的安全恢复副本；丢失它会使所有历史归档无法解密。
- 不删除存储频道、归档主帖、分片回复或封存清单。
- 定期做抽样恢复，并对 D1 索引、KOOK 帖子存在性和清单哈希做巡检。
- 若未来必须获得独立于 KOOK 的灾难恢复能力，应增加第二存储副本；“免费、不限空间、第三方保证永久”无法由应用代码本身保证。
